# Testing strategy

## Testing layers

Testing is layered: pure core unit tests, port contracts, feature integrations, focused UI behavior, and manual Obsidian acceptance. Prefer durable invariants over broad snapshot coverage.

## Critical invariants

Critical invariants include equivalent BOM/line-ending/frontmatter inputs producing the same state, stale asynchronous work never overwriting a newer revision, complete Vault event convergence, shared month/year statistics semantics, reversible periodic path rules, and independent mutable setting arrays and nested configuration objects.

Every bug fix starts with a reproduction. Coverage reveals gaps but does not replace contract tests.

The runtime-i18n boundary must prove that `auto` uses Obsidian's public configured-language API even when the browser locale differs; an unknown Obsidian language falls back to English.

NoteIndex port and integration tests pin the following failure model. Deduplicated initial paths reserve revisions up front and run under the default 16-worker bound. Workers share an 8 ms default time slice and yield one host macrotask together when it expires; a deterministic injected-yield contract proves that no next read group starts and no staged result publishes during that yield, after which the separate staging area still merges atomically and publishes once only after every read succeeds or fails explicitly. Live events during the scan advance path revisions immediately, but ordinary create/modify operations publish through microtask intent and completion batches without exposing staged initial results. Delete and rename first form an immediate old-path invalidation barrier. Contracts cover concurrent-refresh reuse within one revision, create→modify, create→delete, delete→recreate, A→B→C, out-of-order completion across revisions, a slow file not blocking unrelated changes, late deletion results, discarded pending work across stop/restart lifecycles, extension-changing renames, `refresh()` joining the correct promise, and preservation of older snapshots. A subscription, path-listing, or internal-initialization exception must remove the subscription and every half-started state, after which the same instance can start successfully. A modify with the same canonical document performs one read/document parse but skips full domain derivation and public publication; error recovery and rename force full parsing. A high-cardinality projection regression pins last-change-wins per path, complete task-bucket and interval ordering, at most one sub-snapshot revision per batch, identity retention for a no-op batch, and use of the same batch boundary by initial and live commits. Adapter tests pin the `cachedRead()` boundary with a structural fake Vault without introducing the Obsidian runtime into core.

Readiness regressions additionally pin `indexing` before initial completion, `ready` after the atomic startup boundary, a live unknown-path wave returning to `indexing`, and restoration to `ready` only after the injected quiet checkpoint sees no pending intents, reads, queues, or batches. Calendar-store tests prove that a readiness-only snapshot recomputes unknown visible periodic paths from missing to indexing without rematerializing notes, while parsed/error entries retain their meaning. Presentation tests distinguish the muted dashed indexing marker from the error-color missing marker, and command acceptance must prove that an unknown path cannot create a periodic note.

Persistent-cache contracts use a metadata-capable fake source and injectable cache/schedulers. They require matching `path + mtime + size` entries to restore before any verification read, changed or startup-dirtied paths to read before `ready`, deleted paths to disappear without a read, malformed snapshots to clear and fall back to a complete scan, and cache writes to coalesce without source documents or frontmatter. Snapshot and entry-count sidecar are saved and cleared in one current-Vault transaction; status reads only the sidecar or a legacy `getKey()` existence check, while the next normal save backfills legacy metadata. Explicit rebuild waits for a ready, idle immediate save and propagates save failure instead of reporting a stale empty status. Deep cache validation and later full verification both share the initial 8 ms host-yield budget. Verification begins in a later host task, repairs same-metadata external edits, publishes nothing for an unchanged derived note, and yields to a pending or in-flight live revision. Invalid schema, duplicate paths, non-finite metadata, malformed interval date keys, interval boundaries or day counts that disagree with canonical re-parsing, path/task mismatches, and inconsistent task statistics invalidate the snapshot. Raw task date-marker strings intentionally retain cold-parse semantics; impossible dates are ignored by the date projection instead of invalidating an otherwise reusable cache. IndexedDB absence and storage errors must fail open. Warm-cache benchmarks report restored entries, reads before fast readiness, and whether full verification was scheduled; they do not present fast readiness as avoided eventual I/O.

Cache-maintenance contracts distinguish unavailable IndexedDB, no current-Vault record, a valid stored record, a legacy record with unknown count, invalid sidecar metadata, and a read error; empty must never be reported as unavailable. Deletion is bounded by the exact key formed from the current Vault name and storage identity, with tests proving that other Vaults and unrelated IndexedDB keys remain intact. Lifecycle regressions cover repeated rebuilds, coalesced concurrent requests, restoring the index and source subscription after a clear failure, refreshing stored status only after immediate persistence completes, visible save failure, one recovery retry after the first restart failure, visible failure after two restart failures, and preventing an old instance from restarting when unload or runtime replacement occurs during clearing. The settings-section cleanup must also release its button/status subscription.

Integration regressions combine the real `ObsidianNoteSource` with a controllable fake Vault and complete `cachedRead()` calls out of order across initial→modify, pending modify→rename, and pending modify→delete. They prove that an old read cannot overwrite a newer publication or revive an invalidated path. This pins adapter event mapping and the NoteIndex revision barrier, not real Obsidian cache invalidation after external synchronization; rapid desktop/mobile edits and sync remain a manual release gate. When `refresh()` encounters a queued missing intent, it commits the deletion barrier first and then performs an explicit read under a newer revision; tests pin listeners observing missing before that read's parsed or error result becomes authoritative.

Settings contracts cover sequential Chrono Notes Calendar schema v1–v18 migration, treating missing and invalid versions as v1, leaving future versions undowngraded, preserving valid values, dropping unknown fields during final normalization, migration idempotence, and independent input, default-array, and nested-object references. Schema v15 proves the shared confirmation field is removed without translating its value and that the periodic and range strict-boolean toggles normalize independently. Schema v16 proves that legacy task annotation maps `none` to disabled and both `color` and `hole` to enabled, removes the legacy field, and strictly normalizes the new boolean. Schema v17 uses a released schema-v15 fixture to preserve ordered `calendarOverlays` as `calendarExtensions`, convert all five documented Luxon periodic paths into Moment paths, retain templates and unrelated holiday/ICS values, leave valid Moment and unrecognized custom patterns unchanged, remove both legacy fields, and restore Note Navbar recognition for every periodic level. Schema v18 proves that older configurations receive `system` date/time selections plus valid custom-pattern defaults and that valid existing values in all four fields are preserved. Manual Obsidian acceptance injects representative older and invalid data into the isolated vault, performs a full reload, verifies preservation and fallback across all five settings tabs, then saves the current schema and proves that array settings do not alias each other.

Shared confirmation-orchestration contracts prove cancellation does not save, ordinary confirmation does not save, only confirmed suppression persists, and cascades do not prompt again. Structural Vault and Workspace tests cover adapter boundaries; manual Obsidian acceptance still covers real modals, the command palette, and themes.

Lifecycle contracts require an existing pre-current settings object to persist its normalized current-schema snapshot during startup. They also require this write to fail open: the migrated runtime remains available and the original error is logged when persistence rejects.

- When `minAppVersion`, Obsidian API or DOM adapters, lifecycle, settings, or major-view interactions change, rerun the related disable/enable, reload, and unload matrix in both minimum-supported Obsidian 1.12.7 and the latest stable desktop release.
